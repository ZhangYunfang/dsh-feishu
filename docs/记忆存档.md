本机 CLI 安装约定（2026-10-22 实测，可复用）：①自制命令放 `~/bin`（chmod 700，含口令就别给 755）；②PATH 用标记块写进 `~/.zshrc` 与 `~/.bash_profile`：`# >>> into_supervisor: put ~/bin on PATH (managed by DSH) >>>` + `if [ -d "$HOME/bin" ]; then case ":$PATH:" in *":$HOME/bin:"*) ;; *) export PATH="$HOME/bin:$PATH" ;; esac; fi` + `# <<<`，幂等可重跑；③**关键**：登录/交互 shell 会 source rc，但 agent、cron、`ssh host cmd` 这类非交互上下文不会——`bash -c 'command -v X'` 会找不到。`/usr/local/bin` 在 macOS 属 `root:wheel` 不可写，而 `/opt/homebrew/bin` 可写且已在所有 shell 的 PATH 里，所以正解是 `ln -sfn ~/bin/<cmd> "$(brew --prefix)/bin/<cmd>"` 做兜底（不需要 sudo）。④**反复踩的坑**：中英混排 shell 脚本里 `$VAR` 后紧跟中文全角字符（如 `$U）`、`$CONF_HOME（`）会被 bash 当作变量名的一部分，`set -u` 下直接 `unbound variable` 报错；写脚本时变量一律 `${VAR}`，改完用一小段 Python 正则扫一遍「`$NAME` 后一字节 >127」的位置。本机现有 `into_supervisor`（~/bin + 软链）即按此约定安装。

[2026-10-22] [summary:supervisor 面板卡死根治：前置门卫 + 内部端口，规则与 Host 头跳转要点]
supervisor 面板「一直加载」的根治方案（2026-10-22 本机实测，可复用）：supervisord 的 `[inet_http_server]` 是 Medusa 明文服务，收到**非 HTTP 字节（如 TLS ClientHello）或半截请求时既不回应也不超时也不关连接**，该 TCP 在 supervisord 内永久挂住；Medusa 单线程 + Chrome 每主机 6 连接上限 ⇒ 攒够 6 条面板永久转圈（实测 `curl -k https://127.0.0.1:9001/` 8 秒零响应）。正解＝**前面加一层门卫**：supervisord 面板绑回环内部端口（9011），对外入口（9001）由自写 asyncio 转发器接管，规则「首字节大写字母 + 5s 内凑齐完整请求头(空行结尾) + 首行 METHOD path HTTP/1.x + header≤8KB + 并发≤32」才转发，首字节 `0x16` 立即断开 —— 永远不为畸形流量建立上游连接，所以不会攒僵尸（实测 20 条 TLS/半截攻击持续 8s，上游 ESTABLISHED 恒为 0，面板全程 200）。两个上手要点：①3101 转发的跳转地址不用改，因为 supervisor 的 `get_server_url()` 优先用 `Host:` 头（`supervisor/http.py:305-325`），浏览器仍看到 `:9001`；②`logtail/*` 本身是流式长连接，页面转圈是设计行为，需靠空闲超时（120s）兜底。门卫要由 supervisor 自己托管（priority 早启动、autorestart、独立日志），kill -9 后约 1.5s 自愈。实现与验收细节见 `/Users/zyf/Project/DSH_WorkSpace/supervisor-macos/conf/scripts/panel_proxy.py` 与部署指南 §11.9。

[2026-10-22] [summary:浏览器打不开本地端口但 curl 正常＝系统代理吃 127.0.0.1（Chrome 不认 127.* 通配），改用 localhost]
macOS 上「浏览器打不开本地服务、但 curl 一切正常」的头号原因＝系统代理吃掉了 127.0.0.1（2026-10-22 本机实证）：`scutil --proxy` 显示 Wi-Fi 上开着 `127.0.0.1:7892` 全局代理，其「绕过代理」列表里用的是 `127.*`、`10.*`、`172.2*`、`*zhihu.com` 这类写法——**Chrome 的 ProxyBypassRules 只认字面主机名、`*.domain`、CIDR（如 `10.0.0.0/8`）、`<local>`**，`127.*` 这种中段通配被当作无效规则忽略，于是 `http://127.0.0.1:PORT` 被浏览器当外网请求交给代理 → 502 或无限转圈，而 proxy 日志/服务端日志里**一条请求都没有**（这是最快的判别特征）。诊断三连：①`scutil --proxy` 看 HTTPEnable/HTTPProxy/HTTPPort；②`curl -x http://<代理>:<端口> http://127.0.0.1:<端口>/` 复现浏览器行为；③`curl --noproxy '*' http://localhost:<端口>/` 对照。**正解：改用 `http://localhost:<端口>`**（`localhost` 通常在绕过列表里且是合法规则，同时把自己的服务双栈监听 `127.0.0.1` + `::1`）；要保留 IP 访问就 `sudo networksetup -setproxybypassdomains "Wi-Fi" 127.0.0.1 <原有条目...>`（会替换整表）或走 GUI「网络→Wi-Fi→详细信息→代理→忽略这些主机与域」。教训：**curl 不读系统代理，只信 curl 会误判成服务端故障**；给用户交付本地面板类工具时，一律以 `localhost` 作为对外 URL，并把代理拦截检测做进自检命令。

[2026-10-27] [summary:OAuth 回调死循环常见根因：鉴权闸门 cookie 用 SameSite=Strict，跨站跳回时不发送 → 改 Lax]
macOS 浏览器 OAuth 回调"重定向次数过多"的一个非典型根因：本地鉴权插件（如 dsh-web-startup-auth）用 303 + Set-Cookie 给未认证请求补 cookie，但 cookie 设了 SameSite=Strict。从外部 IdP（飞书/GitHub 等）跳回 localhost 属跨站顶层导航，Strict cookie 不会被发送 ⇒ 闸门反复铸 cookie 反复 303 ⇒ ERR_TOO_MANY_REDIRECTS。判别快照：curl -si <回调路径> 若返回 303 且 location 指向自身，就是这类闸门（而不是业务回调）。正解是把该 cookie 改成 SameSite=Lax（Lax 对顶层 GET 跳转放行）。注意补丁在 node_modules 里，插件更新会覆盖。另：curl -L 不带 cookie jar 也会跑满重定向上限，别把它当唯一证据。
